# Native service catalog

Open `/app/services` after native sign-in. Discovery reads retained traces within the current service, environment and team scope. Each catalog identity includes all three values. A replacement runtime version is discovered under the same identity; a deployment in a different environment remains a separate identity with its own versions, request summaries and dependency evidence. Matching service names alone never establish an edge. The catalog reports observed versions, per-endpoint request and error counts, rates over the selected absolute time window, and nearest-rank p50, p95 and p99 durations in original nanoseconds. Only server and consumer spans count as requests. Identical trace and span copies contribute once; conflicting identities are omitted and reported. Parent identities establish observed dependencies; missing, conflicting or out-of-scope parents and unobserved call targets remain unresolved.

The versioned native-session API is `GET /api/porthole/v1/services`, with an optional identity at `GET /api/porthole/v1/services/{id}`. The static OpenAPI artifact describes query bounds and errors. The Services screen links to the same absolute window, intake watermark and scan budget through this API. `from` and `through` are inclusive Unix nanoseconds; their defaults select the previous 24 hours. `snapshot` fixes the completed intake watermark. `budget` is 200 through 2000, in multiples of 200. The response marks a truncated scan as partial. This functional slice does not establish upstream completeness: all values are observed retained traffic, never authoritative full-traffic RED. Missing data cannot establish zero full-traffic errors or healthy service state. Freshness is the age of the last retained span: over five minutes is stale. No retained evidence is reported explicitly, even when reviewed metadata remains.

Service configuration is under Settings, linked from the selected service. A current native owner with fresh identity proof reviews the exact assignee, repository, criticality and runbook before saving. `POST /api/porthole/v1/services/{id}` requires the current metadata revision, all reviewed fields and `confirm` equal to `save-service-metadata`. The initial revision is zero. Reassignment requires an existing active member whose current scope covers the service. An empty owner reference explicitly unassigns it. Metadata changes do not alter membership, dataset access or the destination document's permissions. Runbook and repository links require HTTPS and refuse embedded credentials; ordinary query parameters and document anchors are preserved. The server never fetches them. External links omit native cookies and referrers.

Every successful change creates an immutable audited revision. Stale revisions, foreign origins, bearer credentials (also with a cookie), forbidden roles and ineligible owners refuse without a metadata change. Current native authority applies again on every read. Queries use the configured analytical worker, with no local fallback when it is unavailable. Final source-record checks prevent erased input from being released as an accumulated catalog result. No detached telemetry aggregate is stored.

Product archives retain exact metadata history as inactive context. Restore quarantines all revisions, creates no source memberships or credentials, and cannot activate ownership authority. A new native owner review is required to replace restored context. Source sessions are never portable.

Large stock-capture archive packets retain the same rows, order and digest across restart, retries and inactive restoration. Their packet cache can reference the already frozen rows instead of duplicating a combined packet into one D1 cell. Conflicting restore retries refuse without advancing staging. Existing erasure withdraws those frozen rows and references together.

Observed associations come from the same authorized retained spans. Explicit host, container, Kubernetes pod and runtime-instance resource identities describe where a service ran. Database client spans report their declared system, namespace and server address; messaging spans report their declared system, destination and producer or consumer relationship. Missing identities remain unknown. Each association reports its span-observation count and last observation time; these are neither request totals nor a complete asset inventory. Every association includes an original trace and span reference for its most recent observation. The native Services link opens that trace at the same completed intake watermark. It is an example observation, not a complete list of associated operations. The trace door applies current scope independently; following a reference grants no additional authority. Connection strings, query statements and message bodies are never projected into associations. Association data confers no infrastructure or database access.

Each service also shows unresolved firing context from existing active count monitors whose complete scope the reader already holds. The first recorded firing evaluation fixes the historical service metadata revision; the current reviewed revision is shown separately, so editing a runbook or criticality updates the response context without rewriting its history. Missing historical metadata stays unavailable. A recorded Firing or Unknown episode is not a present-health assertion. The catalog neither creates detection nor requests outbound delivery. Metadata changes grant no monitor access, and following either runbook link still requires destination authorization. Restart retains the original episode; inactive restored monitors contribute no active context. The telemetry snapshot bounds the observed catalog, while metadata and firing context are checked at the current read time.

An empty observation window retains reviewed metadata with explicit missing evidence and unavailable latency. Existing approved homogeneous local erasure removes the spans that supply associations; no detached association survives, and the original wire replay remains fenced after restart. Unrelated service observations remain intact. The existing erasure door continues to refuse configured analytical replicas; this catalog adds no deletion or retention authority.

Datadog full-traffic stats and the identical-window PORT-062 comparison, original SLO comparison, complete infrastructure and database qualification beyond observed semantic identities, imported repository definitions, default detection, investigation notices and outbound alert continuity remain unproved. This catalog enables no outbound action, monitor, SLO change, erasure or expiry policy.
